## 🇩🇪 Deutsch

### Die Bahn kommt jetzt aus dem Simulator

Bisher lag der Landebewertung eine Datenbank zugrunde: Lage, Kurs und Breite jeder Bahn kamen aus den Navdaten. Der Pilot landet aber nicht in einer Datenbank, sondern in der Szenerie, die auf **seinem** Rechner installiert ist. Wo beides auseinanderlief, war die Bewertung schlicht falsch beraten.

Wie weit es auseinanderläuft, haben wir gemessen — im Bestand von 86.674 Bahnen:

| Befund | Anzahl |
|---|---|
| Kurs steht auf 0°/360° (Platzhalter) | 3.836 |
| davon im Widerspruch zur eigenen Bahnkennung | 3.329 |
| Kurs weicht um 3° oder mehr ab | 3.653 |
| Breite weicht um 5 m oder mehr ab | 7.279 |

Ab dieser Version fragt der Client **den laufenden Simulator**, wie die Bahn dort wirklich liegt, und benutzt dessen Antwort. Für **X-Plane** wird die installierte Szenerie in der Reihenfolge gelesen, in der der Simulator sie selbst benutzt — deine Add-on-Plätze schlagen die Standardszenerie, genau wie im Flug. Für den **Microsoft Flight Simulator** fragt der Client die Daten beim Anflug direkt über SimConnect ab, aus derselben Quelle, aus der der Simulator die Bahn zeichnet.

Zugeordnet wird ausschließlich über die **Position** der Schwelle (bis 200 m). Ursprünglich sollte zusätzlich der Kurs übereinstimmen — das war ein Zirkelschluss: Der kaputte Kurs hätte darüber entschieden, ob er repariert werden darf. In BISL hätte er genau eine der beiden Bahnrichtungen repariert und die andere mit demselben Fehler stehen lassen.

Jede Übernahme wird am Flug vermerkt (`bahn_geometrie_quelle`) — es bleibt nachvollziehbar, welche Zahl aus welcher Welt kam.

### Ausfahrten ebenfalls aus der Szenerie

Die Rollwege für die Ausfahrtserkennung kamen aus einer dritten Welt: einer Bodenkarte, die der Server aus OpenStreetMap baut. Dort standen **167 namenlose Ausfahrten an 68 Plätzen**, sieben Plätze hatten gar keine. Die installierte X-Plane-Szenerie führt dagegen **243.945 benannte Rollwegkanten an 6.114 Flughäfen**.

Ab jetzt hat die Szenerie Vorrang; die Serverkarte bleibt als Rückfall. Eine **leere** Szenerie-Karte verdrängt sie ausdrücklich nicht — sonst sähe eine Bahn plötzlich so aus, als hätte sie keine Ausfahrten.

### Fragwürdige Achse: physikalische Regel statt geeichter Zahl

Die Prüfung „passt unsere Bahnachse zur Bahn im Simulator?" hing an einer an Beispielen abgestimmten Zahl. Sie verfehlte den Flug EWG6850 um 0,3 m — eine Zahl, die auf ihre Beispiele passt, ist kein Maßstab.

Jetzt entscheidet die **befestigte Fläche**: Ein Versatz zählt erst als Datenfehler, wenn er größer ist als die halbe Bahnbreite — das Flugzeug wäre dann rechnerisch neben der Bahn gerollt, was es nachweislich nicht war. Ist die Breite unbekannt, bleibt es beim Winkel allein. Geprüft an 56 echten Landungen, die im Programmbestand liegen und bei **jedem** Testlauf mitlaufen.

### Was das für dich ändert

- Landungen an Plätzen, deren Navdaten schlecht sind, werden wieder **bewertet** statt übersprungen — darunter FACT und EDHE.
- Bahnlänge, Aufsetzpunkt und Achsentreue rechnen gegen die Bahn, die du vor dir siehst.
- Ausfahrten werden auch dort erkannt, wo OpenStreetMap nichts hatte.

Der Grundsatz bleibt: Ein Fehler in den Daten darf nie zu einer härteren Note führen.

### Für die Nachwelt

Die Kette „Simulator → Bahn → Bewertung" war beim Bauen an einer Stelle **still** unterbrochen: Die gelesene Szenerie wurde nicht am Flug abgelegt. Die Bahn wäre korrigiert gewesen, die Ausfahrten wären weiter aus OpenStreetMap gekommen — ohne Fehlermeldung. Die Gegenprobe blieb grün; keine Prüfung fing es. Jetzt tut es eine.

Genau dieselbe Klasse traf uns dreimal an einem Tag: Werte, die mit einem Rückfall lautlos verschwinden. Deshalb gilt hier inzwischen: gemessen wird das Ergebnis, nicht der Rückgabewert, und jede Wache muss sich rot machen lassen, indem man entfernt, was sie bewacht.

## 🇬🇧 English

### The runway now comes from the simulator

Until now, landing scoring rested on a database: every runway's position, heading and width came from navdata. But pilots don't land in a database — they land in the scenery installed on **their** machine. Wherever the two disagreed, scoring was simply misinformed.

We measured how far they disagree, across all 86,674 runways:

| Finding | Count |
|---|---|
| Heading is 0°/360° (placeholder) | 3,836 |
| …of those, contradicting their own runway designator | 3,329 |
| Heading off by 3° or more | 3,653 |
| Width off by 5 m or more | 7,279 |

From this version the client asks **the running simulator** where the runway actually is, and uses that answer. For **X-Plane** the installed scenery is read in the same order the simulator itself uses it — your add-on airports beat the default scenery, exactly as in flight. For **Microsoft Flight Simulator** the client requests the data on approach via SimConnect, from the very source the simulator draws the runway from.

Matching is done **by threshold position** alone (within 200 m). The original design also required the heading to agree — that was circular: the broken heading would have decided whether it may be repaired. At BISL it would have fixed one runway direction and left the other with the identical defect.

Every adoption is recorded on the flight (`bahn_geometrie_quelle`), so it stays traceable which number came from which world.

### Exits come from the scenery too

Taxiways for exit detection came from a third world: a ground map the server builds from OpenStreetMap. It held **167 unnamed exits across 68 airports**, and seven airports had none at all. The installed X-Plane scenery, by contrast, carries **243,945 named taxiway edges at 6,114 airports**.

Scenery now takes precedence, with the server map as fallback. An **empty** scenery map explicitly does not displace it — otherwise a runway would suddenly look as though it had no exits.

### Questionable axis: a physical rule instead of a tuned constant

The check "does our runway axis match the runway in the simulator?" hung on a constant tuned against examples. It missed flight EWG6850 by 0.3 m — a number that fits its own examples is not a yardstick.

Now the **paved surface** decides: an offset counts as a data error only once it exceeds half the runway width — the aircraft would then have been taxiing off the runway, which demonstrably it wasn't. Where width is unknown, the angle alone still applies. Verified against 56 real landings that live in the repository and run on **every** test run.

### What changes for you

- Landings at airports with poor navdata are **scored** again instead of skipped — FACT and EDHE among them.
- Runway length, touchdown point and centreline tracking are computed against the runway you actually see.
- Exits are detected even where OpenStreetMap had nothing.

The principle stands: a flaw in the data must never produce a harsher grade.

### For the record

While building it, the chain "simulator → runway → scoring" was **silently** broken in one place: the scenery that had been read was never stored on the flight. The runway would have been corrected while exits kept coming from OpenStreetMap — with no error anywhere. The counter-check stayed green; no test caught it. One does now.

That same class hit us three times in a single day: values that vanish quietly behind a fallback. Hence the rule we now work by — measure the result, not the return value, and prove every guard by removing what it guards and watching it go red.

### Für VA-Betreiber / For VA operators

Keine Serverarbeit nötig. Die neuen Felder (`bahn_geometrie_quelle`, `bahn_kurs_korrektur_grad`, `bahn_breiten_korrektur_m`) sind rein zusätzlich; ältere Recorder ignorieren sie.

No server work required. The new fields are purely additive; older recorders ignore them.
