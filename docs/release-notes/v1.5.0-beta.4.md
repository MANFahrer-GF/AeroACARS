## 🇩🇪 Deutsch

Kleine, gezielte Nachbesserung an beta.3. Beide Punkte kommen aus dem ersten
Feldtest und betreffen nur den Panel-Server.

### Der Log beantwortet jetzt die naheliegendste Frage

Als das In-Sim-HUD auf „Keine Verbindung" stand, konnte die Logdatei nicht
sagen, ob der Panel-Server überhaupt lauscht: es gab nur eine Zeile für den
Fehlerfall, und deren Fehlen ließ beide Deutungen offen. Es gibt jetzt eine
Meldung bei Erfolg (`panel_server: listening`) und eine beim Auslösen des
Stopp-Signals. Damit steht die Antwort in der Datei statt in einer Vermutung.

Nebenbefund aus derselben Untersuchung: Der Fehler lag **nicht** in AeroACARS.
Der Server lauschte, antwortete in 43 ms und lieferte vollständige Daten. Die
Ursache saß im Flow-Widget, das hängende Anfragen stapelte und damit die
Verbindungsplätze des Simulators verstopfte. Behoben auf Widget-Seite, ohne
Änderung am Client.

### Panel-Server stoppt erst beim echten Beenden

Das Stopp-Signal hing bisher an `ExitRequested`. Das heißt nur „jemand möchte
beenden" und kann abgelehnt werden — der Server konnte also ausgehen, während
die App weiterlief, und das HUD hätte aus diesem Zustand nie zurückgefunden.
Jetzt hängt es an `Exit`, das erst beim tatsächlichen Ende der
Ereignisschleife feuert und nicht mehr abgelehnt werden kann. Der eigentliche
Zweck bleibt gewahrt: der Server hält an, bevor der Anwendungszustand abgebaut
wird.

### Panel-Server lauscht jetzt auf zwei Rückschleifen-Adressen

Zusätzlich zu `127.0.0.1` auch auf `::1`. Grund aus dem Feldtest: Anfragen aus
dem Simulator blieben irgendwann dauerhaft hängen — keine Antwort, kein Fehler.
Der eingebettete Renderer führt seinen Verbindungsvorrat pro Ziel-Adresse; ist
der einmal mit toten Steckplätzen belegt, kommt über diese Adresse nichts mehr
durch. Eine zweite Adresse gibt dem In-Sim-HUD einen davon unabhängigen Weg,
ohne dass der Simulator neu gestartet werden muss.

Die Sicherheitseigenschaft bleibt unverändert: `::1` ist genauso Rückschleife
wie `127.0.0.1` und vom Netzwerk aus unerreichbar. Ein Test sichert das ab.
Schlägt eine der beiden Bindungen fehl, läuft die andere weiter.

### Zum Absturz

Weiterhin **ungeklärt**. Die in beta.3 genannte Vermutung ist durch die neue
Logdatei widerlegt: der Panel-Server ging dort gemeinsam mit MQTT im selben
Millisekundenschritt aus, also bei einem völlig normalen Beenden. Für die
Klärung braucht es ein Speicherabbild. Die Logdatei aus beta.3 bleibt dafür
das zweite wichtige Beweismittel.

### Für VA-Betreiber

Keine Änderung am Datenformat zum Server. `aeroacars-live` muss **nicht**
mit-deployed werden.

## 🇬🇧 English

A small, targeted follow-up to beta.3. Both items come out of the first field
test and touch only the panel server.

### The log now answers the obvious question

When the in-sim HUD showed "no connection", the log file could not say whether
the panel server was listening at all: there was only a line for the failure
case, and its absence left both readings open. There is now a message on
success (`panel_server: listening`) and one when the stop signal fires. The
answer is in the file instead of in a guess.

Side finding from the same investigation: the fault was **not** in AeroACARS.
The server was listening, answered in 43 ms and returned complete data. The
cause sat in the Flow widget, which stacked hanging requests and exhausted the
simulator's connection slots. Fixed on the widget side, with no client change.

### The panel server now stops only on a real exit

The stop signal used to hang off `ExitRequested`. That only means "someone
would like to quit" and can be declined, so the server could go down while the
app kept running, leaving the HUD in a state it would never recover from. It
now hangs off `Exit`, which fires only when the event loop actually ends and
cannot be declined. The original purpose is preserved: the server stops before
the application state is torn down.

### The panel server now listens on both loopback addresses

`::1` in addition to `127.0.0.1`. Reason from the field test: requests from the
simulator eventually hung permanently — no response, no error. The embedded
renderer keeps its connection pool per target address; once that pool is filled
with dead slots, nothing gets through on that address any more. A second
address gives the in-sim HUD an independent path without requiring a simulator
restart.

The security property is unchanged: `::1` is loopback just as `127.0.0.1` is,
and unreachable from the network. A test guards this. If either bind fails, the
other keeps serving.

### On the crash

Still **unexplained**. The hypothesis stated in beta.3 has been disproven by
the new log file: the panel server went down there together with MQTT within
the same millisecond, i.e. during a perfectly normal shutdown. Confirming the
cause needs a crash dump. The beta.3 log file remains the second piece of
evidence.

### For VA operators

No wire-format change. `aeroacars-live` does **not** need to be deployed
alongside this build.
