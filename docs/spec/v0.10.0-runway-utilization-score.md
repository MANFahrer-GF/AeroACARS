## Pflicht-Vorgaben

### Datenquellen (alle bereits im Touchdown-Payload, verifiziert für EK406)

| Feld | Type | Quelle | Zweck in dieser Spec |
|---|---|---|---|
| `td_distance_from_threshold_m` | `f64` | Forensik | Distanz Touchdown-Punkt zu Schwelle |
| `landing_float_distance_m` | `f32` | Forensik | Floating-Distanz (50 ft → TD) — informativ, NICHT im Numerator (siehe LE1) |
| `rollout_distance_m` | `f32` | Forensik | TD-Punkt → Stop, Meter |
| `runway_length_m` | `f32` | Navigraph | Physische Bahn-Länge |
| `runway_displaced_threshold_ft` | `i32` | Navigraph | Versetzte Schwelle in Fuß |
| `pre_displaced_threshold` | `bool` | Forensik | TD VOR der Schwelle aufgesetzt (= illegale Landung) |

| `aircraft_icao` | `Option<String>` | Bid + Sim-Snapshot | nur Heavy-Allowance-Modifier |

**Keine MQTT-Wire-Erweiterung nötig** — alle Felder schon im Schema.

## Leitentscheidungen

### LE1 — Numerator: TD-Punkt-bis-Stop, NICHT nur Rollout

**Korrektur QS-R1-P0:** Originaler R0-Draft hatte `rollout / runway_length` — semantisch falsch. Ein Pilot der 1500 m floated und dann nur 200 m brakes hätte fälschlicherweise 200 m Rollout = perfekt, obwohl er die Bahn-Marge total weggeworfen hat.

**Korrekte Definition** (kompatibel zu v0.8.4 Runway-Usage-V2 in den Release-Notes):

```
distance_used_m = td_distance_from_threshold_m + rollout_distance_m
```

= „von der Landeschwelle bis zum Stillstand" = total used landing distance.

`landing_float_distance_m` bleibt in der UI als **separate Info-Zeile** ("davon ~520 m Float vor Aufsetzen"), aber zählt **nicht doppelt** in den Numerator (TD-Distanz enthält den Float schon implizit: ein langer Float = großes `td_distance_from_threshold_m`).

### LE2 — Denominator: Landing Distance Available (LDA)

```
LDA_m = runway_length_m - (runway_displaced_threshold_ft × 0.3048)
```

Wenn `runway_displaced_threshold_ft` `None` oder 0 → `LDA_m = runway_length_m`.

**Begründung:** Nutzbare Landung beginnt an der Schwelle (= ggf. displaced), nicht am physischen Bahn-Anfang. EDDF 25C hat z.B. 4000 m physisch aber 600 m displaced → LDA = 3400 m. Bei dieser Spec scoren wir gegen die 3400 m.

### LE3 — Sonderfall `pre_displaced_threshold = true`

Pilot setzt VOR der displaced Schwelle auf (= regelwidrig in den meisten Ländern, betrifft Wing-Tip-Vortex-Avoidance + Lärmschutz). `td_distance_from_threshold_m` wird in diesem Fall **negativ** sein (vom Forensik-Code so geliefert).

**Score-Verhalten:**
- `distance_used_m` wird über `clamp_min(rollout_distance_m)` abgesichert → minimaler Numerator = nur Rollout, aber niemals negativ
- Sub-Score-Wert wird mit Rationale `"pre_displaced_threshold"` (NEU) gerendert + Warn-Pill in der UI, unabhängig vom Score-Band
- Pilot sieht: „⚠ Vor Displaced-Threshold aufgesetzt — Score-Korrektur unsicher, bitte Anflugprofil prüfen"

### LE4 — Score-Bänder, **exakt definiert** (QS-R1-P1)

```
ratio_pct = (distance_used_m / LDA_m) × 100.0
ratio_pct_rounded = ratio_pct.round() as i32   // halb-aufwärts gerundet, IEEE-754-default
effective_pct = ratio_pct_rounded - heavy_allowance_pp
```

`heavy_allowance_pp = 5` für Heavy-Aircraft (LE5), sonst `0`.

**Vergleichs-Operatoren** (eindeutig, keine 30 vs 30.0001 Frage):

| Band | Bedingung auf `effective_pct` | Pkt | Rationale-Key |
|---|---|---|---|
| `excellent_margin` | `effective_pct < 30` | 100 | `landing.rat.excellent_margin` |
| `good_stop` | `30 <= effective_pct < 50` | 80 | `landing.rat.good_stop` |
| `ok_stop` | `50 <= effective_pct < 70` | 55 | `landing.rat.ok_stop` |
| `long_rollout` | `70 <= effective_pct < 90` | 25 | `landing.rat.long_rollout` |
| `marginal_runway` | `90 <= effective_pct <= 100` | 5 | `landing.rat.marginal_runway` |
| `overrun_risk` (NEU) | `effective_pct > 100` | 0 | `landing.rat.overrun_risk` |

- `100 %` exakt → `marginal_runway` (= darüber gibt's keine Bahn mehr, max-Reserved-Score wäre 5)
- `>100 %` → `overrun_risk` (= rein rechnerisch Pilot ist über Bahnende rausgerollt; in real-life wäre das ein Overrun-Report. Wir machen 0 PTS + dedicated Rationale).
- Raw `ratio_pct` wird in der UI angezeigt (auch falls > 100), nicht das clamp'd effective_pct.

### LE5 — Heavy-Allowance, **als Reduktion benannt**

**Klarstellung QS-R1-P1:** Heavy bekommt eine **Allowance** (= Bonus, weniger streng). Nicht Penalty.

```
effective_pct = raw_ratio_pct - allowance
allowance = 5  if aircraft is Heavy else 0
```

**Beispiele:**
- Heavy mit Raw-Ratio 30 % → effective 25 % → `excellent_margin` (100 PTS).
  Ohne Allowance hätte er auch `excellent_margin` bekommen wenn `<30`-Grenze, mit Allowance auch wenn raw=34.
- Heavy mit Raw-Ratio 50 % → effective 45 % → `good_stop` (80 PTS).
  Ohne Allowance wäre er bei `ok_stop`. Heavy wird also bei 50 % nicht „bestraft".
- Medium A320 mit 50 % → effective 50 % → `ok_stop` (55 PTS). Standard-Behandlung.

Heavy-Set bleibt identisch zur heutigen `landing-scoring::category_for_icao`-Liste (Wide-Bodies + B747 + MD11 + IL96 + Antonov). Light/Medium ohne Allowance.

### LE6 — Skip-Gate: Score wird **nicht** vergeben wenn

QS-R1-P1 erweitert von „missing length" auf vollständige Trust-Bedingung:

```
SKIP if (
    runway_length_m is None
    || !runway_geometry_trusted
    || airport_source != "runway_match"
    || LDA_m <= 0   // Datenfehler-Schutz
)
```

`SubScoreEntry::skipped("rollout", reason: …)` mit konkretem Skip-Grund. Im UI als „nicht bewertet — Bahn-Daten unvollständig" sichtbar, kein Score-Beitrag.

**Kein Meter-Backup-Fallback** (QS-R1-Antwort 6). Lieber ehrlich „kein Score" als irreführend.

### LE7 — Single Source of Truth (SSoT) — **eine Implementation, zwei Renderer**

**Korrektur QS-R1-P0:** R0 sagte „byte-identisch in 3 Stellen". Falsch gedacht.

**Korrekt:**

```
┌─ Rust-Crate: landing-scoring/src/sub_rollout.rs ─────────────┐
│  EINZIGE Stelle die Score COMPUTED                            │
│  - Pilot-Client ruft sub_rollout() einmal pro Touchdown       │
│  - Ergebnis wird in TouchdownPayload.sub_scores[] geschrieben │
└───────────────────────────────────────────────────────────────┘
                              │ MQTT
                              ▼
┌─ Recorder ─────────────────────────────────────────────────────┐
│  Speichert sub_scores als-is, kein Re-Compute                  │
└────────────────────────────────────────────────────────────────┘
                              │ HTTP
                              ▼
┌─ Render-Surfaces ──────────────────────────────────────────────┐
│  webapp/src/components/landingScoring.ts  ← NUR Render-Types   │
│  client/src/lib/landingScoring.ts         ← NUR Render-Types   │
│  - Tippen die SubScore-Wire-Struct                             │
│  - Mappen rationale_key → i18n-Label                           │
│  - Renderen Wert + Punkte + Band-Farbe                         │
│  - NIE Score nachrechnen — wenn payload.sub_scores fehlt:      │
│    skipped-Block anzeigen, NICHT lokal computen                │
└────────────────────────────────────────────────────────────────┘
```

**Konsequenz:**
- `computeSubScores()` in beiden TS-Files wird **entfernt**. Webapp + Client lesen nur `payload.sub_scores` und rendern.
- F18/F19-Bug-Klasse („verschiedene Sub-Score-Tabellen in 3 Stellen") wird **architektonisch ausgeschlossen**.
- Backward-Compat: alte PIREPs ohne `sub_scores`-Array → kein Bahn-Auslastung-Block (skipped), kein Versuch nachzurechnen.

### LE8 — Cross-Sync per Schema-Sync, nicht per Logik-Sync

Da die Logik nur in Rust lebt, bleibt nur die **Wire-Struktur** als Sync-Punkt:

- Rust `SubScoreEntry`-Struct ist die Wahrheit
- Webapp + Client haben TypeScript-Interfaces die diese widerspiegeln
- **CI-Test:** Rust-Test exportiert `SubScoreEntry`-Schema als JSON-Schema → Build-Step generiert daraus die TS-Interfaces unter `shared/landing-scoring-wire.ts` → TS-Compile bricht wenn ein Render-Surface ein nicht-existierendes Feld referenziert.
- Pragmatisch für v0.10.0: wir machen den Generator **NICHT** automatisch, sondern dokumentieren das Wire-Format in der Spec + dem Rust-Code als „MUST NOT CHANGE without bumping VERSION_WIRE". Generator-Implementierung ist v0.11.0-Roadmap.

### LE10 — Migration: **forward-only** (QS-R1-P2)

- Alte PIREPs behalten ihre gespeicherten `sub_scores` (falls vorhanden) ohne Recompute.
- Ab v0.10.0-Update werden alle neuen Touchdowns mit dem neuen Algorithmus gescort.
- **Kein Re-Score-Tool** für historische Daten (= einfacher, keine UI-Verwirrung „warum hat sich mein 2-Wochen-alter Score geändert").
- Webapp Landing-Detail erkennt am `ux_version`-Feld (oder einem neuen `score_algorithm_version`) ob sub_scores nach altem oder neuem Algo entstanden sind und zeigt entsprechend.

### LE11 — Inspirations-Quelle ehrlich benannt (QS-R1-P2)

Die 30/50/70/90-Bänder sind **AeroACARS-Policy**, inspiriert von Runway-Safety-Konzepten (TALPA-OFDA-Reporting verwendet ähnliche Stufen). **Keine offiziell zertifizierte Aviation-Spec.** Im CHANGELOG + Pilot-Tooltip entsprechend formulieren.

## Algorithmus (Rust-Pseudo-Code)

```rust
pub fn sub_rollout(input: &RolloutInput) -> SubScoreEntry {
    // Skip-Gate (LE6)
    if input.runway_length_m.is_none() {
        return SubScoreEntry::skipped("rollout", "missing_length");
    }
    if !input.runway_geometry_trusted.unwrap_or(true) {
        return SubScoreEntry::skipped("rollout", "untrusted_geometry");
    }
    if input.airport_source.as_deref() != Some("runway_match") {
        return SubScoreEntry::skipped("rollout", "off_airport_landing");
    }

    let runway_m = input.runway_length_m.unwrap();
    let displaced_m = input.runway_displaced_threshold_ft.unwrap_or(0) as f32 * 0.3048;
    let lda_m = runway_m - displaced_m;
    if lda_m <= 0.0 {
        return SubScoreEntry::skipped("rollout", "invalid_lda");
    }

    // Numerator (LE1) + pre_displaced-Schutz (LE3)
    let td_dist = input.td_distance_from_threshold_m.unwrap_or(0.0) as f32;
    let rollout = input.rollout_distance_m.unwrap_or(0.0);
    let mut distance_used = (td_dist + rollout).max(rollout); // niemals negativ

    let raw_ratio_pct = (distance_used / lda_m) * 100.0;
    let raw_pct_rounded = raw_ratio_pct.round() as i32;

    // Heavy-Allowance (LE5)
    let allowance = if is_heavy(input.aircraft_icao.as_deref()) { 5 } else { 0 };
    let effective_pct = raw_pct_rounded - allowance;

    // Banding (LE4)
    let (points, rationale, band) = match effective_pct {
        e if e < 30  => (100, "excellent_margin", Band::Good),
        e if e < 50  => ( 80, "good_stop",        Band::Good),
        e if e < 70  => ( 55, "ok_stop",          Band::Ok),
        e if e < 90  => ( 25, "long_rollout",     Band::Bad),
        e if e <= 100 => ( 5, "marginal_runway",  Band::Bad),
        _            => (  0, "overrun_risk",     Band::Bad),
    };

    let value = format!("{} m / {} m  ·  {} %", 
                        distance_used.round() as i32, 
                        lda_m.round() as i32, 
                        raw_pct_rounded);
    
    let mut extra = vec![];
    if let Some(float) = input.landing_float_distance_m {
        extra.push(format!("davon ~{} m Float vor Aufsetzen", float.round() as i32));
    }
    if let (Some(icao), Some(ident)) = (&input.runway_match_icao, &input.runway_match_ident) {
        extra.push(format!("Bahn: {} {}, LDA {} m", icao, ident, lda_m.round() as i32));
    }

    let warning = if input.pre_displaced_threshold.unwrap_or(false) {
        Some("Vor Displaced-Threshold aufgesetzt — Anflugprofil prüfen".to_string())
    } else { None };

    SubScoreEntry::scored("rollout", "landing.sub.rollout", points, value, rationale, band)
        .with_extra(extra)
        .with_warning(warning)
}
```
