# v0.9.3 — GlitchTip Emit-Sites (Pilot-Client)

**Status:** DRAFT R0 — addresses Lücken aus `v0.9.0-glitchtip-self-hosted.md` für die Implementation
**Autor:** v0.10.x-Session-Owner
**QS-Reviewer:** Thomas Kant (VA-Owner)
**Trigger:** Eigenes Eingeständnis nach v0.9.2 — GlitchTip-Plumbing ist live, aber **kein einziges Custom-Event** wird tatsächlich gesendet (nur Rust-Panics + React-ErrorBoundary). ---

## Ziel

Pilot-Client v0.9.3 sendet bei den 9 wichtigsten User-impacting Fehler-Klassen ein anonymisiertes Custom-Event an `tip.kant.ovh`. Damit:

1. **VA-Owner sieht Bugs bevor Piloten sie melden** (Adrian/Svenny-Pattern wäre in ≤15 min sichtbar gewesen).
2. **GlitchTip-Investition (v0.9.0/v0.9.1/v0.9.2 Plumbing) wird produktiv** — nicht nur Theorie.
3. **Keine Privacy-Regression** — Allowlist + Redaction aus v0.9.0 bleibt hart durchgesetzt.
4. **Keine Quota-Explosion** — Rate-Limiting verhindert dass MQTT-Reconnect-Loops oder ähnliche „Storm"-Pattern das Daily-Quota in 30 Sekunden verbrennen.

## Pflicht-Vorgaben

### Existierende Infrastruktur (NICHT verändern)

- `sentry_init::capture_message(msg, level)` + `sentry_init::capture_error(&e)` — Wrapper existieren bereits, sind aber **mit `#[allow(dead_code)]` geflaggt weil von niemand gerufen** (siehe `sentry_init.rs:351-361`). Diese Spec entfernt die Dead-Code-Marker indem sie Aufrufer einbaut.
- Privacy-Vertrag aus `v0.9.0-telemetry-contract.md` Sektion 9 (DSGVO-Gates) bleibt unverändert.

### Was diese Spec NICHT macht

- Keine neue Sentry-SDK-Version, keine neuen Dependencies
- Keine UI-Änderung (Consent-Toggle bleibt wie er ist)
- Keine Webapp-Sites, keine Recorder-Sites (= eigene Specs später, sind in v0.9.0-Spec sowieso schon umrissen)
- Keine Tag-Allowlist-Erweiterung (alle 9 Sites kommen mit den schon erlaubten Tag-Keys aus)

## Leitentscheidungen

### LE1 — Site-Liste pragmatisch auf 9 Pilot-Client-Sites

Aus den 11 Sites der v0.9.0-Spec wählen wir **9 die heute funktional emittierbar sind** und für jede `error.code` definiert ist. Eine Site (`Forensic-only Bounce`) wird zurückgestellt weil sie für die Top-Pain-Points (Pilot kann nicht updaten, Pilot bekommt falschen Score, PIREP kommt nicht durch) nicht relevant ist — kann in v0.9.4 nachgereicht werden.

Plus eine Site **NEU** die in v0.9.0-Spec fehlte aber Adrian-Pattern relevant ist: **Auto-Update-Check-Fail**.

| # | Site | Severity | Trigger | error.code |
|---|---|---|---|---|
| S1 | PIREP-Submit-Fail transient | Warn | HTTP 5xx oder Network-Timeout im `file_pirep_with_retry`-Loop, NACH 3 Versuchen scheitert | `pirep_file_failed_transient` |
| S2 | PIREP-Submit-Fail hard | Error | HTTP 4xx ohne Retry (validation/auth), oder Final-Failure in Background-Worker | `pirep_file_failed_hard` |
| S3 | SimConnect-Disconnect | Info | Pipe-Break / Reconnect-Loop-Start (= einmal pro Loop, NICHT pro Retry-Versuch) | `sim_disconnect` |
| S4 | Aircraft-Mismatch | Warn | Pilot startet Flug mit anderem Aircraft als gebid (vor Acknowledge) | `aircraft_mismatch` |
| S5 | not_at_departure | Warn | Pilot drückt Auto-Start, ist aber > 5 nm vom planned dep entfernt | `not_at_departure` |
| S6 | Hard Landing | Warn | V/S ≤ -600 fpm oder Peak-G ≥ 1.70 bei Touchdown | `hard_landing` |
| S7 | Auto-Update-Check-Fail | Info | Tauri-Updater HTTP-Fehler beim `latest.json`-Fetch (Network/4xx/5xx) | `update_check_failed` |
| S8 | Recorder-Upload-Fail | Warn | MQTT-Publish failed nach Retry-Loop (touchdown/pirep — NICHT position weil das laufend ist) | `recorder_upload_failed` |
| S9 | DDS-Violation (Touchdown vor Displaced-Threshold) | Warn | `pre_displaced_threshold = true` im Touchdown-Payload — VA-Owner sieht „Welche Piloten landen regelmäßig zu früh" | `dds_violation` |

**Reihenfolge der Implementation:** S1 → S2 → S3 → … → S9, in genau dieser Order. Jede Site ein atomarer Commit (Code + Test + Doc-Eintrag), jeder Commit live gegen tip.kant.ovh verifizierbar bevor der nächste startet.

### LE2 — Rate-Limiting: Token-Bucket pro `error.code`

**Problem:** ohne Limit könnte ein MQTT-Reconnect-Storm 100×/s `S8` triggern → Daily-Quota leer + tip.kant.ovh-Dashboard unbedienbar.

**Lösung:** zentraler Token-Bucket pro `error.code`-String. Default-Config:

```rust
// in client/src-tauri/src/sentry_init.rs (NEU)
const RATE_LIMIT_DEFAULTS: &[(&str, RateLimit)] = &[
    // (error.code, RateLimit { max_per_window, window_seconds })
    ("pirep_file_failed_transient", RateLimit { max: 3, secs: 300 }),   // 3 / 5min
    ("pirep_file_failed_hard",      RateLimit { max: 5, secs: 60 }),    // 5 / min (hart wollen wir sehen)
    ("sim_disconnect",              RateLimit { max: 1, secs: 60 }),    // 1 / min (Reconnect-Loops koalesziert)
    ("aircraft_mismatch",           RateLimit { max: 5, secs: 60 }),
    ("not_at_departure",            RateLimit { max: 5, secs: 60 }),
    ("hard_landing",                RateLimit { max: 10, secs: 60 }),
    ("update_check_failed",         RateLimit { max: 1, secs: 600 }),   // 1 / 10min (laufender Check)
    ("recorder_upload_failed",      RateLimit { max: 3, secs: 60 }),
    ("dds_violation",               RateLimit { max: 10, secs: 60 }),
];

// Fallback wenn error.code nicht in Liste: max=10, secs=60
```

**Implementierung:** `HashMap<String, BucketState>` mit `BucketState { tokens_remaining, window_started_at }`. Vor `capture_message`-Call: `try_consume_token(error_code)`. Wenn `false` returnt → Event verwerfen + `tracing::debug!` loggen. Wenn `true` → durchsenden.

**Sentry-SDK eigene Rate-Limits** bleiben unverändert (HTTP 429-Response respektieren). Unser Token-Bucket ist eine ZUSÄTZLICHE Defense.

### LE3 — Aufrufer-Pattern: helper-Funktion `report_event!`-Makro

Statt 9× `sentry_init::capture_message(...)` mit ähnlichem Tag-Setup-Boilerplate, ein einziges Helper-Makro:

```rust
// in client/src-tauri/src/sentry_init.rs (NEU)
#[macro_export]
macro_rules! report_event {
    (
        level = $level:expr,
        code = $code:expr,
        message = $msg:expr
        $(, $tag_key:ident = $tag_val:expr)* $(,)?
    ) => {
        $crate::sentry_init::emit_with_rate_limit(
            $level,
            $code,
            $msg,
            &[$((stringify!($tag_key), $tag_val.into())),*],
        )
    };
}
```

Verwendung an Site:

```rust
report_event!(
    level = sentry::Level::Warning,
    code = "pirep_file_failed_transient",
    message = "PIREP file failed (transient — will retry)",
    pirep_id = &flight.pirep_id,
    error_status_code = status.as_u16().to_string(),
);
```

**Vorteile:**
- Konsistente Tag-Reihenfolge across Sites
- Rate-Limiting + Allowlist-Enforcement an EINER Stelle
- Mock-bar für Tests (= `emit_with_rate_limit` lässt sich überschreiben)
- Wenn jemand vergisst die Allowlist zu pflegen, scheitert der Build (`tag_key:ident` macht Compile-Time-Check unmöglich, aber das `tag_key.into()` zur Laufzeit + before_send-Hook strippt unbekannte Keys → max kosmetischer Bug, kein Privacy-Leak)

### LE4 — Test-Strategie: 3-Schichten pro Site

**Schicht 1: Unit-Test im `sentry_init`-Modul** — `emit_with_rate_limit` mit Mock-Hub. Prüft Rate-Limiting-Verhalten (Token-Verbrauch, Window-Reset).

**Schicht 2: Pro-Site Integration-Test** — Code-Pfad mockt den auslösenden Fehler (= HTTP-400-Mock für S1/S2, Sim-Disconnect-Event für S3, etc.) und prüft dass das richtige Event-Konstrukt an den Mock-Hub gegangen ist. Eines pro Site.

**Schicht 3: DEV-Trigger-Tauri-Commands** (NUR in DEV-Builds via `#[cfg(debug_assertions)]`):

```rust

#[tauri::command]
fn dev_trigger_glitchtip_event(site: String) -> Result<String, String> {
    match site.as_str() {
        "pirep_fail_transient" => report_event!(...),
        "pirep_fail_hard"      => report_event!(...),
        "sim_disconnect"       => report_event!(...),
        ...
        _ => return Err(format!("unknown site: {site}")),
    }

```

Frontend bekommt einen **versteckten DEV-Panel-Section** (nur in `import.meta.env.DEV`) mit 9 Buttons. VA-Owner kann jedes Event manuell auslösen und in tip.kant.ovh innerhalb 15 Sek verifizieren.

**Production-Build hat die Buttons NICHT.** Cleaner als der v0.9.3-Test-Event-Button-Versuch (der lag offen für alle Pilots).

### LE5 — Akzeptanz pro Site

Eine Site ist „done" wenn ALLE 4 Kriterien erfüllt sind:

| Kriterium | Wie verifizieren |
|---|---|
| (a) `cargo test`-Integration-Test grün | CI-Job-Status |
| (b) DEV-Trigger-Button löst sichtbares Event in `tip.kant.ovh` aus innerhalb 15 Sek | Manuell via VA-Owner-Browser |
| (c) Allowlist-Compliance (KEIN Tag außerhalb der erlaubten Liste im gesendeten Event) | Network-Inspector im Browser-DevTools beim Test-Button-Click |
| (d) Rate-Limit greift (= 5× nacheinander triggern → max 1 Event pro Window erscheint) | DEV-Button 5× klicken, in tip.kant.ovh zählen |

Wenn (b) failt: Site rollt zurück bis (b) grün ist. Wir akzeptieren KEINEN „lokal grün, in tip.kant.ovh nicht sichtbar"-Status — das wäre der gleiche Bug-Mechanismus wie Svenny-Modal.

### LE6 — Reihenfolge & atomarer Commit pro Site

Jede der 9 Sites bekommt einen eigenen Commit + PR-Review. Reihenfolge:

1. **S1 + S2 zusammen** (PIREP-Submit-Fail) — höchster Pain-Wert, gleiche Code-Stelle, ein Test deckt beide
2. **S3** (SimConnect-Disconnect) — zweithäufigste Pain-Source
3. **S4** (Aircraft-Mismatch)
4. **S5** (not_at_departure)
5. **S6** (Hard Landing)
6. **S7** (Auto-Update-Check-Fail) — Adrian/Svenny-Pattern direkt adressiert
7. **S8** (Recorder-Upload-Fail)
8. **S9** (DDS-Violation)

**Vor jeder Site:** PR-Title sagt `feat(glitchtip): S{N} — {site name}`. Body enthält Akzeptanz-Checkliste (a)-(d).

**Nach jeder Site:** Live-Verifikation gegen tip.kant.ovh (DEV-Trigger oder echter Auslöser falls einfach reproduzierbar). Erst dann nächste Site.

### LE7 — Privacy-Vertrag bleibt hart

Allowlist aus `sentry_init::allowed_tag_keys()` wird nicht erweitert. Wenn eine Site einen Tag schicken will der nicht erlaubt ist:

- **Option A:** Tag rauslassen (= Wert kommt nicht in Event)
- **Option B:** Allowlist erweitern, ABER nur mit Spec-Eintrag in `v0.9.0-telemetry-contract.md` Sektion 1 + QS-Runde

Diese Spec führt **keine Allowlist-Erweiterungen** ein — alle 9 Sites kommen mit dem heutigen Set aus (`error.code`, `error.kind`, `error.status_code`, `simulator`, `aircraft`, `airport`, `runway`, `pirep.id`, `callsign`, `phase`, `pilot.hash`, `forensics.version`, `distance.bucket`).

## Algorithmus (Helper-Funktionen)

### `emit_with_rate_limit()` — Kernfunktion

```rust
// in client/src-tauri/src/sentry_init.rs (NEU)
pub fn emit_with_rate_limit(
    level: sentry::Level,
    error_code: &'static str,
    message: &str,
    tags: &[(&str, String)],
) -> bool {
    // Consent-Gate (= globaler Atomic). Wenn aus → silent skip.
    if !CONSENT.load(Ordering::Relaxed) {
        return false;
    }
    // Rate-Limit-Gate
    if !try_consume_token(error_code) {
        tracing::debug!(
            error_code,
            "[sentry] rate-limited — event dropped before send"
        );
        return false;
    }
    // Send
    sentry::with_scope(
        |scope| {
            scope.set_tag("error.code", error_code);
            for (k, v) in tags {
                scope.set_tag(k, v);
            }
        },
        || {
            sentry::capture_message(message, level);
        },
    );
    true
}

fn try_consume_token(error_code: &str) -> bool {
    static BUCKETS: OnceLock<Mutex<HashMap<&'static str, BucketState>>> = OnceLock::new();
    let mut buckets = BUCKETS.get_or_init(|| Mutex::new(HashMap::new())).lock().unwrap();
    let limit = RATE_LIMIT_DEFAULTS
        .iter()
        .find(|(k, _)| *k == error_code)
        .map(|(_, l)| *l)
        .unwrap_or(RateLimit { max: 10, secs: 60 });
    let now = Instant::now();
    let entry = buckets.entry(error_code).or_insert(BucketState {
        tokens_remaining: limit.max,
        window_started_at: now,
    });
    if now.duration_since(entry.window_started_at).as_secs() >= limit.secs {
        // Window expired → reset
        entry.tokens_remaining = limit.max;
        entry.window_started_at = now;
    }
    if entry.tokens_remaining > 0 {
        entry.tokens_remaining -= 1;
        true
    } else {
        false
    }
}
```

## Offene Fragen für R0-Review

1. **Site S9 (DDS-Violation):** soll das wirklich per Event laufen oder reicht's wenn es im `touchdowns.payload_json` steht und der VA-Owner per SQL-Query reportet? Pro-Argument für Event: Discord-Webhook-Integration in tip.kant.ovh ist „kostenlos" (= VA-Owner sieht's sofort statt monatlichen SQL-Audit). Contra: keine Eskalations-Severity, mehr Noise im Dashboard.
