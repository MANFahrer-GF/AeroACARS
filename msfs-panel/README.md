# AeroACARS MSFS In-Sim Panel (feasibility-spike build)

Spec: [`docs/spec/msfs-ingame-landing-debrief-panel.v1.yaml`](../docs/spec/msfs-ingame-landing-debrief-panel.v1.yaml).

This package talks to AeroACARS's **existing** LAN Remote Control server
(`client/src-tauri/src/remote/`, port 8765 by default) — no new server, no
new routes. It is a **thin client** of two already-existing endpoints:

- `POST /api/auth {pin}` — pairing (same PIN shown in AeroACARS's
  Settings → Fernzugriff panel).
- `GET /ws?token=...` — the existing 1Hz `flight_status` push, now
  carrying an extra `live` telemetry sub-object.
- `POST /api/cmd/landing_get_current` — pulled once per landing, after
  scoring finalizes.

**The central open question this build exists to answer:** does Coherent
GT (MSFS's in-game UI engine) actually allow `fetch()`/`WebSocket` calls to
`127.0.0.1` from an in-sim toolbar panel at all? This is documented as an
unresolved, community-wide unknown (see the spec's `feasibility_spike`
section) — not something this repo can verify without a real MSFS 2024
install. That's what testing this build answers.

## What's here vs. what still needs the Windows MSFS SDK

Everything in this folder is real source, not a placeholder — `manifest.json`,
the `Build/PackageSources/aeroacars-panel.xml` panel definition, and the full
`html_ui/InGamePanels/AeroACARSPanel/` HTML/CSS/JS. What's **missing** is
`layout.json` (MSFS's package file index) and the compiled `.spb` — both are
generated by Microsoft's MSFS 2024 SDK tooling, not hand-authored, and that
tooling only runs on Windows.

## Build steps (Windows, with the MSFS 2024 SDK installed)

1. Install the MSFS 2024 SDK (in-sim: Options → General → Developer Mode →
   enables the SDK; or via the standalone installer from the Xbox/MS Store
   MSFS SDK page).
2. Open **Project Editor** (part of the SDK) and load
   `Build/PackageDefinitions/aeroacars-panel.xml`.
3. **Build All Packages.** This regenerates `layout.json`, computes
   `total_package_size` in `manifest.json`, and compiles
   `Build/PackageSources/aeroacars-panel.xml` into
   `InGamePanels/aeroacars-ingamepanel.spb`.
4. The Project Editor's output package folder (typically
   `Build/Packages/aeroacars-msfs-panel/` after a build — exact path shown
   in the Project Editor's build log) is what goes in Community.

## Install (manual, for this spike — no auto-installer yet)

Copy the **built output package folder** (not this source folder) into your
MSFS 2024 Community folder. Community folder location:

- Steam: `%APPDATA%\Microsoft Flight Simulator 2024\Packages\Community`
- MS Store / Xbox app: read `InstalledPackagesPath` from
  `%LOCALAPPDATA%\Packages\Microsoft.Limitless_8wekyb3d8bbwe\LocalCache\UserCfg.opt`,
  then look for `Community` under that path — the default value varies by
  install, so reading `UserCfg.opt` is more reliable than assuming a fixed
  path (see the spec's platform_scope_note research).

An auto-installer (`msfs_panel_install.rs`, mirroring the existing
X-Plane plugin installer in `client/src-tauri/src/xplane_plugin_install.rs`)
is deliberately **not built yet** — no point automating an install step
before we know the core networking assumption above holds. See
`docs/spec/msfs-ingame-landing-debrief-panel.v1.yaml` `feasibility_spike`
for what "done" looks like before that's worth building.

## Testing the spike

1. Start AeroACARS, enable "Fernzugriff" (LAN Remote Control) in Settings —
   note the port (default 8765) and PIN.
2. Launch MSFS 2024 with the built package in Community.
3. Look for the AeroACARS icon in the MSFS toolbar. Open it.
4. Enter the PIN. **Report exactly what happens** — success, a fetch
   error, a silent hang, anything — this is the actual spike result.
5. If pairing succeeds but the WebSocket never receives data, that's the
   `websocket_live` risk materializing (SHOULD-009's polling fallback in
   `panel.js` should kick in automatically after a few failed WS retries —
   check whether IT works, too).
6. Open the Coherent GT Debugger (SDK tool) on the panel while testing to
   see the actual console/network errors, if any — far more informative
   than guessing from the panel's own UI.

Report back (even "nothing happened, blank panel") — that's real
information either way.
