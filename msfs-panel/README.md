# AeroACARS MSFS In-Sim Panel (feasibility-spike build)

Spec: [`docs/spec/msfs-ingame-landing-debrief-panel.v1.yaml`](../docs/spec/msfs-ingame-landing-debrief-panel.v1.yaml).

This package talks to AeroACARS's **existing** LAN Remote Control server
(`client/src-tauri/src/remote/`, port 8765 by default) — no new server, no
new routes. It is a **thin client** of two already-existing endpoints:

- `POST /api/auth {pin}` — pairing (same PIN shown in AeroACARS's
  Settings → Fernzugriff panel).
- `GET /ws?token=...` — the existing 1Hz `flight_status` push, now
  carrying an extra `live` telemetry sub-object.
- `POST /api/cmd/landing_get_current` — pulled once per landing, after
  scoring finalizes.

**The central open question this build exists to answer:** does Coherent
GT (MSFS's in-game UI engine) actually allow `fetch()`/`WebSocket` calls to
`127.0.0.1` from an in-sim toolbar panel at all? This is documented as an
unresolved, community-wide unknown (see the spec's `feasibility_spike`
section) — not something this repo can verify without a real MSFS 2024
install. That's what testing this build answers.

## What's here vs. what still needs the Windows MSFS SDK

Everything in this folder is real source, not a placeholder — `manifest.json`,
`Build/PackageDefinitions/aeroacars-panel.xml` (Project Editor build config),
`Build/PackageSources/InGamePanels/aeroacars-panel.xml` (the panel
definition) and `Build/PackageSources/html_ui/` (the full HTML/CSS/JS).
What's **missing** is `layout.json` (MSFS's package file index) and the
compiled `.spb` — both are generated by Microsoft's MSFS 2024 SDK tooling,
not hand-authored, and that tooling only runs on Windows.

**Round-1 field test (2026-08-08) update:** the structure above (two
AssetGroups splitting the panel `.spb` from `html_ui`, `Dependencies`,
`PackageOrderHint`) was fixed based on what actually built and rendered
in-sim on a real Windows/MSFS-2024 rig — see the spec's
`feasibility_spike.round_1_packaging_fixes` for exactly what changed and
why. This README's build steps below are updated to match; the one thing
NOT yet re-verified after this restructure is a fresh end-to-end build —
round 2 should build clean from this current source before anything else.

## Build steps (Windows, with the MSFS 2024 SDK installed)

1. Install the MSFS 2024 SDK: in-sim, Options → General → Developer Mode.
   **Correction from round 1:** MSFS 2024, unlike 2020, has no standalone
   `ProjectEditor.exe` — Project Editor only runs in-sim once Developer Mode
   is on (Devmode menu bar → Tools, or File → New/Open Project). It closes
   again every time MSFS restarts and has to be reopened + the project
   reloaded via "Open Recent" each session.
2. Open a project pointed at `Build/PackageDefinitions/aeroacars-panel.xml`.
   Round 1 hit a Project-Editor import bug: "Import Item" on an existing
   package-definition XML sometimes creates a *file* named
   `PackageDefinitions` instead of a folder containing the XML — if that
   happens, delete it, create the `PackageDefinitions\` folder by hand, and
   copy the XML in yourself.
3. **Build All Packages.** This launches a brief partial MSFS instance
   internally (the compilers live in the sim) — normal, wait it out. It
   regenerates `layout.json`, computes `total_package_size`, and compiles
   the panel definition into `InGamePanels\aeroacars-ingamepanel.spb`.
4. The project's own `Packages\` output folder (path shown in the build
   log) is what goes in Community — Project Editor does **not** copy it
   there automatically, that's a manual step every time.

## Install (manual, for this spike — no auto-installer yet)

Copy the **built output package folder** (not this source folder) into your
MSFS 2024 Community folder. Community folder location:

- Steam: `%APPDATA%\Microsoft Flight Simulator 2024\Packages\Community`
- MS Store / Xbox app: read `InstalledPackagesPath` from
  `%LOCALAPPDATA%\Packages\Microsoft.Limitless_8wekyb3d8bbwe\LocalCache\UserCfg.opt`,
  then look for `Community` under that path — the default value varies by
  install, so reading `UserCfg.opt` is more reliable than assuming a fixed
  path (see the spec's platform_scope_note research).

An auto-installer (`msfs_panel_install.rs`, mirroring the existing
X-Plane plugin installer in `client/src-tauri/src/xplane_plugin_install.rs`)
is deliberately **not built yet** — no point automating an install step
before we know the core networking assumption above holds. See
`docs/spec/msfs-ingame-landing-debrief-panel.v1.yaml` `feasibility_spike`
for what "done" looks like before that's worth building.

## Testing the spike

1. Start AeroACARS, enable "Fernzugriff" (LAN Remote Control) in Settings —
   note the port (default 8765) and PIN.
2. Launch MSFS 2024 with the built package in Community.
3. Look for the AeroACARS icon in the MSFS toolbar. Open it. **Round 1
   confirmed this part works** — the panel renders correctly (title, status
   line, PIN field, button).
4. **First check: can you actually type into the PIN field now?** Round 1
   found MSFS's own control bindings eat keystrokes in toolbar-panel text
   fields unless the panel explicitly claims focus via
   `Coherent.trigger('FOCUS_INPUT_FIELD', ...)` — a fix for that is in
   `panel.js` now but was never live-verified (see
   `feasibility_spike.round_1_new_blocker` in the spec). If typing still
   doesn't work, that's the next thing to debug, not the network question
   yet.
5. Once you can type: enter the PIN. **Report exactly what happens** —
   success, a fetch error, a silent hang, anything — THIS is the actual
   spike result we still don't have.
6. If pairing succeeds but the WebSocket never receives data, that's the
   `websocket_live` risk materializing (SHOULD-009's polling fallback in
   `panel.js` should kick in automatically after a few failed WS retries —
   check whether IT works, too).
7. Open the Coherent GT Debugger (`C:\MSFS 2024 SDK\Tools\CoherentGT
   Debugger\Debugger.exe`) on the panel while testing to see the actual
   console/network errors. Round 1 found it crashes on direct launch
   (missing working directory for its DLL search) — start it with its own
   folder as the working directory. Round 1 also got a blank page after
   entering its `127.0.0.1:19999` URL despite the port showing active
   connections in `netstat` — not resolved; if that recurs, it may not be a
   simple REST/HTTP debugger and might need a different access method.

Report back (even "nothing happened, blank panel") — that's real
information either way.
